A cluster whose nodes are browser tabs

Open the join page and your tab becomes a worker node of a real, Kubernetes-compatible cluster. The scheduler sends it Pods; each one runs in its own Linux VM inside your browser, on the cluster's Pod network, talking peer to peer with Pods in other visitors' tabs. Nothing is installed on your machine, and closing the tab leaves the cluster.

What is gr8s?

gr8s is a Kubernetes-compatible cluster in one executable, written from scratch in Common Lisp, with Prolog for the rules behind its gr8s doctor. The API server, scheduler, controllers, node agent, networking (an eBPF dataplane), DNS, Gateway, storage and the Raft-replicated datastore are all in that one binary. You drive it with kubectl and ordinary manifests, and it passes the upstream Kubernetes conformance tests.

Ordinary nodes

On a Linux machine, a gr8s node runs Pods the way Kubernetes does, with containerd and runc. This demo's own server is one: it serves this page.

Browser tab nodes

What's new is a node that is a browser tab. It joins the same cluster, takes Pods from the same scheduler, and puts them on the same Pod network, each Pod in a Linux VM compiled to WebAssembly.

A real Pod network

Pods in your browser have cluster addresses on a network shared with every other node. Tabs connect peer to peer, punching a hole through each other's home routers, so Pods in two visitors' browsers talk directly.

Images over BitTorrent

Container image layers travel between nodes over the BitTorrent protocol, tab to tab as between ordinary nodes, each piece checked against the layer's digest.

gr8s is an experiment: a new Kubernetes-compatible implementation, not a supported product.

How it works

One small server in Nuremberg runs gr8s: the API server, the scheduler, the controllers, a Gateway and a STUN responder. Everything else happens in visitors' tabs.

You join

The join page connects to the server over a WebSocket and proves who it is with a key your browser keeps. A reload is the same node; a closed tab is a node that has gone.

The server makes you a node

Your tab appears in kubectl get nodes as browser-…, arm64, with the capacity it offers. The kubelet's half of the work stays on the server; your tab only runs containers.

Pods arrive

A DaemonSet puts a web server Pod on every tab. Its image's layers come from other tabs where they can, checked piece by piece, and it boots in a Linux VM compiled to WebAssembly.

It serves the world

Anyone opening tabs.demo.gr8s.io gets a page from one of those tabs, after the server has checked it against the image.

Peer to peer

The server introduces tabs to each other, and from then on they talk directly where they can: in this demo, every tab may connect to every other.

Getting through home routers

A tab behind a home router doesn't know its own public address. It asks the server's STUN responder, which answers with the address the request came from. Two tabs swap those addresses through the server and send to each other at the same moment, so each router lets the other's packets in.

Pod traffic

When a Pod in your tab talks to a Pod in another tab, its packets ride a WebRTC data channel straight there, encrypted. Services work the same way: your tab picks a backend and rewrites the address, as a node's kernel would.

Image layers, shared like torrents

Each layer of a container image is a torrent in the same BitTorrent protocol gr8s's own nodes use. A tab fetches pieces from other tabs, rarest first, checks each one against its digest, and passes on what it has. The server seeds every piece too, so a layer always arrives.

When direct fails

Some networks, mobile ones especially, won't let two tabs connect. Then traffic simply goes through the server, as it did before the tabs met. Nothing breaks; it takes the long way.

Checked content

Whoever runs a tab controls it, and could make its Pod serve anything. So the page at tabs.demo.gr8s.io isn't passed on blindly. The server pulled the image itself and knows every file in it. For each request it asks one tab's Pod, and passes the answer on only when it is that file, byte for byte. A tab that answers anything else is refused, and its node is tainted so its Pods leave.

The page then says which tab served it, which browser, and how long it has been up: facts the server fills in after the check, not the tab.

Safety and privacy

  • Your machine stays yours. Pods run in VMs inside your browser's sandbox, with no access to your files or other tabs. Close the tab and they are gone.
  • Pods can't reach the internet. In this demo they reach only each other and cluster DNS, so a tab is no relay for anyone.
  • Tabs get no secrets. Browser nodes refuse Pods that bring Kubernetes Secrets, host paths or privileges. Private images are pulled by the server; their credentials never reach a tab.
  • Other tabs see your public address. Tabs that connect directly learn each other's public IP address, as any WebRTC call does. The join page says so.
  • Tab owners don't see web visitors' addresses. Your tab's Pod logs which browser asked for a page, but not who: the server doesn't forward visitors' IP addresses to tabs.
  • It's a demo. At most 64 tabs at once, and 4 from one address. It may be restarted at any time; tabs rejoin by themselves.

Try it

Open join.demo.gr8s.io in a tab and leave it open. Under each Pod, “Logs and console” shows what it prints and its Linux VM booting, read from your tab. Then open tabs.demo.gr8s.io in another tab and reload: the page names the tab that served it, sometimes yours.
