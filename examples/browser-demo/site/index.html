gr8s browser nodes demo

A cluster whose nodes are browser tabs

This is a demonstration of gr8s, a Kubernetes-compatible cluster in one executable, and of its ability to run worker nodes in your browser! OK, maybe not so practical, but definitely fun.

Open the join page, and your tab becomes a worker node of the cluster. The scheduler sends it Pods. Each Pod runs in its own Linux VM inside your browser, on the cluster's Pod network, and talks peer to peer with Pods in other visitors' tabs. You install nothing, and when you close the tab, it leaves the cluster.

What is gr8s?

gr8s is a Kubernetes-compatible cluster in one executable, written from scratch in Common Lisp. The one binary holds the API server, scheduler, controllers, node agent, networking (an eBPF dataplane), DNS, Gateway, storage and the Raft-replicated datastore. You use it with kubectl and ordinary manifests, and it passes the upstream Kubernetes conformance tests.

Ordinary nodes

On a Linux machine, a gr8s node runs Pods as Kubernetes does, with containerd and runc. This demo's own server is such a node, and it serves this page.

Browser tab nodes

A browser tab can also be a node. It joins the same cluster and takes Pods from the same scheduler. Its Pods join the same Pod network, each in a Linux VM compiled to WebAssembly.

A real Pod network

Pods in your browser have cluster addresses on a network that every node shares. Tabs punch holes through each other's home routers and connect peer to peer, so Pods in two visitors' browsers talk directly.

Images over BitTorrent

Nodes share container image layers over the BitTorrent protocol, tabs as well as ordinary nodes. Every piece is checked against the layer's digest.

gr8s is an experiment: a new Kubernetes-compatible implementation. It is not a supported product.

How it works

One small server in Nuremberg runs gr8s: the API server, the scheduler, the controllers, a Gateway and a STUN responder. Everything else happens in visitors' tabs.

You join

The join page connects to the server over a WebSocket. It proves who it is with a key that your browser keeps. If you reload, you are the same node. If you close the tab, the node goes.

The server makes you a node

Your tab appears in kubectl get nodes as browser-…, arm64, with the capacity it offers. The server does the kubelet's half of the work. Your tab only runs containers.

Pods arrive

A DaemonSet puts a web server Pod on every tab. The tab gets the image's layers from other tabs where it can, and checks each piece. Then the Pod boots in a Linux VM compiled to WebAssembly.

It serves the world

Anyone who opens tabs.demo.gr8s.io gets a page from one of those tabs. The server first checks the page against the image. Reload it a few times, and you see different nodes serve it.

What runs in your tab

The sample app is an ordinary container image for ARM64 (linux/arm64). It is a small page on Project Hummingbird's minimal, hardened nginx, the same build that Red Hat ships. Nothing in it is made for browsers.

A Linux kernel, compiled to WebAssembly

Each Pod boots its own unkernel: Linux itself, built as one WebAssembly module. Its scheduler, memory management, file systems and TCP/IP are compiled code. Nothing in the kernel is emulated, so nginx gets Linux's own behaviour.

ARM64 programs, JIT-compiled to WebAssembly

The image's programs are unmodified ARM64 binaries. An ARM64 CPU built into that kernel runs them. It compiles their hot code to WebAssembly as they run. So the nginx that serves you a page is the same binary that is in the image.

Peer to peer

The server introduces tabs to each other. After that, they talk directly where they can. In this demo, every tab may connect to every other.

Getting through home routers

A tab behind a home router doesn't know its own public address. It asks the server's STUN responder, which answers with the address the request came from. Two tabs swap those addresses through the server. Then they send to each other at the same moment, so each router lets the other's packets in.

Pod traffic

When a Pod in your tab talks to a Pod in another tab, its packets go straight there over an encrypted WebRTC data channel. Services work the same way. Your tab picks a backend and rewrites the address, as a node's kernel would.

Image layers, shared like torrents

Each layer of a container image is a torrent, in the same BitTorrent protocol that gr8s's own nodes use. A tab gets pieces from other tabs, rarest first, and checks each one against its digest. It also gives other tabs the pieces it has. The server seeds every piece too, so a layer always arrives.

When direct fails

Some networks, mobile ones especially, won't let two tabs connect. Then the traffic goes through the server, as it did before the tabs met. It still arrives, by a longer path.

Checked content

Whoever runs a tab controls it, and could make its Pod serve anything. So the server checks the page at tabs.demo.gr8s.io before it passes it on. The server pulled the image itself, so it knows every file in it. For each request, it asks one tab's Pod for the page. It passes the answer on only when the answer is that file, byte for byte. If a tab answers with anything else, the server refuses the answer and taints the tab's node, so its Pods leave.

The page then says which tab served it, in which browser, and how long that tab has been up. The server fills in these facts after the check. The tab does not.

Safety and privacy

  • Your machine stays yours. Pods run in VMs inside your browser's sandbox. They can't reach your files or your other tabs. When you close the tab, they are gone.
  • Pods can't reach the internet. In this demo, they reach only each other and cluster DNS. So nobody can use a tab to relay traffic.
  • Tabs get no secrets. Browser nodes refuse Pods that bring Kubernetes Secrets, host paths or privileges. The server pulls private images itself, so their credentials never reach a tab.
  • Other tabs see your public address. Tabs that connect directly learn each other's public IP address, as any WebRTC call does. The join page says so.
  • Tab owners don't see web visitors' addresses. Your tab's Pod logs which browser asked for a page, but not who asked. The server doesn't send visitors' IP addresses to tabs.
  • It's a demo. It takes at most 64 tabs at once, and 4 from one address. It can restart at any time. When it does, tabs rejoin by themselves.

Try it

Open join.demo.gr8s.io in a tab, and leave it open. Under each Pod, "Logs and console" shows what the Pod prints and how its Linux VM booted, read from your tab. Then open tabs.demo.gr8s.io in another tab and reload it a few times. The page names the tab that served it, which is sometimes yours.
