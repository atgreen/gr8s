# gr8s security / reliability / availability spot-check — round 2

**Date:** 2026-11-12
**Branch:** `http-client-aggregator`
**Reference:** upstream Kubernetes at `~/git/kubernetes`
**Companion:** `k1.md` (round 1 — request authn/authz, admission, TLS/PKI, secrets, NetworkPolicy, Raft/store)

This round covers the three areas round 1 did not touch, chosen because the 1.37
certification test does not exercise them:

1. **The multi-node / node-agent trust boundary** (newest, uncertified code).
2. **Controllers, garbage collection, finalizers, owner references.**
3. **Kubelet/runtime enforcement** — the gap between "admission allowed it" and "the
   runtime actually applies it."

## Overall assessment

All three areas are, again, **substantially correct**. The two things most likely to have
been security holes are not:

- The node-agent session has a genuine, strong **NodeRestriction equivalent**: the session's
  identity is cryptographically bound to the node's client cert, and per-pod/per-node authority
  is enforced on every write. A node cannot authenticate as, or act as, another node.
- The **admission-vs-runtime gap is essentially closed**: every SecurityContext and resource-limit
  field that PSA validates actually reaches the CRI/containerd spec, `runAsNonRoot` is re-checked
  against the image's resolved UID at container-create time (the check admission cannot do), and
  the subPath escape (CVE-2021-25741) is hardened with `openat2(RESOLVE_BENEATH|RESOLVE_NO_MAGICLINKS)`.
  **No silent privilege grant was found.**

The findings are: one cross-node integrity gap, several availability gaps (connection-exhaustion
DoS, no per-controller error isolation, no node-pressure eviction / QoS-aware OOM), and a set of
defense-in-depth items. None is a remote unauthenticated compromise.

## N1 — Cross-node WireGuard endpoint / relay-source poisoning via self-asserted observations (Medium, security)

`record-authenticated-wireguard-observations` (`src/apiserver/node-session.lisp:924-968`), reached
from the session `:status` handler, lets an authenticated node **A** write a *different* node **B**'s
state. It finds `target` B by matching the reported `peer-public-key` to any registered node's
WireGuard key (`:936-939`), requires `reporter != target` (`:941`), then — on evidence A chooses
freely, `received-bytes > 0` and a `latest-handshake-unix-seconds` within 180s (`:942-943`) —
overwrites B's `nat-reflexive` endpoint (`:954-959`) and refreshes B's relay source-authorization
(`:960-963`), republishing B's topology to all peers (`:964-965`). **Verified**: there is no
cryptographic proof the handshake occurred; A simply asserts it.

Bounds that keep this Medium, not High: the address is validated to a non-loopback unicast IPv4
(`canonical-node-underlay-address`, `scheduler.lisp:199`); writes are rate-limited 1/30s/target
(`accept-wireguard-nat-observation-p`, `:917`); WireGuard's static-key crypto prevents traffic
interception; and the endpoint is a "candidate" that agents still re-gate with their own handshake
probe (comment `:928-929`).

**Impact:** a malicious node can (a) redirect peers' WG handshake-init packets to an arbitrary
unicast IPv4:port (reflection), and (b) destabilize B↔peer connectivity by flipping B's reflexive
candidate and relay source binding. This is the one place the node-agent boundary lets a node speak
about *another* node — the gap vs. k8s NodeRestriction.

**Fix:** require server-side corroboration (e.g. from the target's own session) before mutating a
target node's endpoint, or treat these strictly as non-authoritative hints that never alter relay
authorization.

## N2 — Node listener connection-exhaustion DoS (Medium, availability)

The node gRPC listener uses a single global connection semaphore, default **128**
(`ocicl/ag-gRPC-.../ag-grpc/server.lisp:69-70,334,380-398`); `start-node-grpc-server` passes no
override (`node-session.lisp:1889-1890`). There is **no per-peer/per-node cap**, so one
authenticated node — or, during the 10s handshake window, any peer that can reach a routable
listener including the unauthenticated enrollment service — can occupy all 128 slots and lock every
other node out of Connect/heartbeat.

Compounded by a **session leak**: on reconnect for the same node-name,
`handle-node-connect-internal` replaces the sessions-table entry (`:1398-1401,1437`) but never closes
the previous session's stream/connection, and `evict-silent-node-sessions` (`:1503-1521`) only
targets the currently-registered session — so orphaned handler threads/connections from a node that
holds TCP open accumulate against the 128 cap.

Gating: `:node-listen` defaults to `127.0.0.1` (loopback-only; `server/main.lisp:1905,1931`), so only
a routable node address exposes this remotely — i.e. it bites real multi-node deployments.

**Fix:** per-node-identity connection cap; close the superseded stream on reconnect.

## C2 — No per-controller error isolation (Medium, availability)

**Independently verified.** The leader's `before-reconcile` hook (`src/server/main.lisp:2031-2060`)
runs ~25 controllers as **bare sequential calls** in one lambda. The only error boundary is the
worker loop's single `handler-case` around the *whole* pass (`reconciliation-worker-loop`,
`main.lisp:1712-1720`) — whose own docstring says "one bad pass never kills the *loop*", i.e. it was
designed for loop survival, not per-controller isolation.

So any error that escapes a controller's own internal guard aborts **every controller listed after
it, every pass**, deterministically. `collect-orphaned-api-objects` (position ~13) **re-raises** any
non-404/409 `kubernetes-error` (`garbage-collection.lisp:88`), which is a realistic trigger (a 5xx
from a fail-closed admission webhook, or a type error on a malformed stored object). Everything after
it then starves: `reconcile-workloads`, HPA, endpoints/endpointslices, service-IP/LB/ingress status,
projected-token pruning, and — critically — `publish-service-discovery-snapshots` (runs last). That
last point amplifies the blast radius: a stuck early controller also **halts service-discovery /
NetworkPolicy / DNS projection to all node agents**, so this is not only a control-loop stall but a
data-plane-projection stall.

**Fix:** wrap each controller call in its own logged `handler-case` (or give each its own
worker/workqueue), so one failing controller cannot starve the rest.

## R1 — No node-pressure eviction (Medium, availability)

**Confirmed** — there is no eviction manager and no `MemoryPressure`/`DiskPressure`/`PIDPressure`
node condition anywhere in `src/` (grep returns nothing). The only eviction is per-pod
ephemeral-storage-limit enforcement (`reconciler.lisp:265-327`). Under node memory/disk/PID
pressure, gr8s does **not** proactively, gracefully evict low-QoS pods the way the kubelet does — it
relies entirely on the kernel OOM killer. A real availability deviation invisible to the cert test:
a node under memory pressure gets hard kernel kills instead of graceful, QoS-ordered eviction.

**Fix:** implement a node-pressure eviction manager with the standard signals/thresholds and the
`*Pressure` node conditions.

## C1 — No owner-reference permission enforcement (Low–Medium, security)

gr8s has no equivalent of k8s `OwnerReferencesPermissionEnforcement`. `validate-owner-references`
checks only shape (`src/model/parsing.lisp:242-256`); GC-time deletion is gated only by admission
webhooks, not RBAC (`controller-delete-allowed-p` → `admit-delete`, no authz;
`admission-http.lisp:98-116`). No `blockOwnerDeletion`/ownerReference-permission/finalizers-subresource
authz exists in `src/apiserver`.

Bounded by the (correct) UID + same-namespace owner resolution, so this is not a cross-tenant
*deletion* in the general case. Residual impact: a subject with `update` on a child but no rights on
the owner can set `blockOwnerDeletion: true` to **hold another principal's owner from foreground
deletion** — including a cluster-scoped owner (PV, ClusterRole, Node) referenced from a namespaced
child — an availability lever; and in narrow cases attach a victim object under an owner so GC
deletes it. This is the GC analogue of k1's **F2**. Likely an accepted single-tenant deviation, but
should be explicit.

## R2 — No QoS-based OOM prioritization (Low–Medium, availability)

`oom-score-adj` is never set, so every container ships the proto default `0`
(`container-resources.lisp` omits it; proto initform `0` at `cri-v1-generated.lisp:4913`), and the
sandbox leaves `cgroup-parent` empty (`cri.lisp:230-248`) — no cgroup-per-QoS subtree. The kubelet
sets per-QoS `oom_score_adj` (Guaranteed −998 … BestEffort 1000) so the OOM killer sacrifices
BestEffort first. Combined with R1, behavior under memory pressure does **not** follow QoS — a
Guaranteed pod is about as likely to be OOM-killed as a BestEffort one. (containerd's
`restrict_oom_score_adj=true` at `managed-containerd.lisp:453` only clamps; it does not restore QoS
ordering.)

**Fix:** set per-QoS `oom_score_adj` on containers and/or manage a cgroup-per-QoS hierarchy.

## N3 — Operation responses not bound to the sending session; predictable trace op-ids (Low, security)

In `handle-node-agent-envelope`, the `:operation-response` and `:operation-stream` branches
(`node-session.lisp:1282-1287`) look the operation up purely by `operation-id` in a global table
(`find-node-operation`) and **never** check that the sending node equals the operation's owning
node/session. So any authenticated node that learns another node's in-flight operation-id can inject
a terminal response or fabricated stream bytes (e.g. fake exec/attach output) into that operation.

Exploitability is low because exec/attach/portforward/slynk op-ids come from `generate-uid` =
128-bit CSPRNG. **Exception (verified):** trace op-ids use `(random (expt 36 8))` — `cl:random`,
~41 bits, non-CSPRNG — plus index and node name (`trace-coordinator.lisp:123`), i.e. predictable in
principle.

**Fix:** bind the op-id lookup to the owning session on the inbound path (the data is already on the
struct), and mint trace ids from a CSPRNG.

## N4 — mTLS enforced only when PKI is configured (Low, by-design note for podster-0oc.12)

`authenticate-node-peer` (`src/security/node-tls.lisp:180-194`) and `node-server-tls-options`
(`:72-84`) are both no-ops when `pki` is NIL: the listener is then plaintext and every Connect/
track-image call trusts the hello's `node-name` with no credential. Production always supplies
`:pki pki` (`server/main.lisp:1904,1907`), so this is a test/dev mode, not a shipped exposure — but
nothing *refuses* to serve node sessions when PKI is absent, so a misconfiguration silently yields an
unauthenticated, plaintext node control plane. The mTLS mechanism itself is correct and required
when PKI is present (relevant to **podster-0oc.12**).

**Fix:** refuse to start a node listener without authentication unless a deliberate insecure flag is set.

## R3 — No pids limit (Low, availability)

No per-container/pod `pids.max` is set; gr8s writes nothing to the cgroup-v2 `unified` map and leaves
the pod cgroup to containerd defaults. A fork bomb in one container is not bounded by gr8s. Minor
(k8s normally enforces this via node/pod cgroup config gr8s doesn't manage directly).

## C3 — No per-item backoff/workqueue (Low, info)

No rate-limited workqueue; the leader re-scans all resources every `interval` (default 1.0s,
`main.lisp:1684`). Bounded (no retry storm), and failed-scheduling events are rate-limited to 30s and
Job retries use real exponential backoff — but there's no per-object exponential backoff on transient
write failures, so a hot object retries ~every 1s indefinitely. Low impact; noted for completeness.

## Verified correct (with evidence)

Spot-checks that came back clean, worth recording so effort isn't re-spent:

**Node-agent boundary**
- **Session identity = cert identity (NodeRestriction equivalent).** `verify-node-certificate`
  (`pki.lisp:552-575`) requires CN == claimed node-name, internal-profile + client-auth EKU, a real
  chain to the internal trust anchors, and rejects API-issued certs; run against the hello before the
  session is trusted (`node-session.lisp:1338`). Node A cannot authenticate as node B.
- **Per-pod/per-node authority enforced:** pod-status writes gated on `node-name == pod.nodeName` +
  UID + resourceVersion (`:1239-1242`); credential tokens bound to the node's exact pod + declared SA
  (`:1115-1120`); service-receiver proofs bound to the authenticated node-id, stale/foreign proofs
  voiding the report (`:1036-1064`); device-plugin/extended resources validated (`:1225-1227`).
- **Handshake (podster-dmp):** hello authenticated and all topology inputs validated before any
  durable write; protocol version strict-equality (no downgrade; `node-protocol.lisp:48-55`); 10s TLS
  handshake deadline; per-call session-ticket cache prevents a bootstrap ticket resuming an
  authenticated session (`node-tls.lisp:144-178`).
- **Bootstrap/enrollment limited:** `enroll-node-csr` (`pki.lisp:485-503`) requires a one-time,
  name-bound, role-gated join token + CA-fingerprint pin + a CSR whose subject is forced to the
  validated node name; the issued cert cannot act as another node and cannot by itself open a Connect
  session.
- **CNI local control socket isolated:** mode-0600 + `SO_PEERCRED` with UID == server euid
  (`agent-cni.lisp:70-74,182-188`) — kernel credentials are unspoofable.
- **Reporter's own observations bounded:** `canonical-node-wireguard-observations` caps
  iteration/count and restricts keys to the reporter's own route peers; relay is bounded (max 1024
  channels, per-channel pps/byte limits, idle reaping).

**Controllers / GC**
- GC validates owner **UID** before treating an owner as live (`garbage-collection.lisp:27`,
  `crd-garbage-collection.lisp:28`) — no wrong-UID confused-deputy; namespaced owners looked up in the
  dependent's own namespace; unknown external kinds return `:unknown`, never guessed absent; deletes
  carry the dependent's own UID precondition.
- Orphan/dangling refs patched out while a solid owner survives; foreground/orphan intents durable
  across restart/HA failover (replicated via Raft).
- Controllers run only behind the Raft leader gate with consensus-committed, optimistic-concurrency
  writes — no lease split-brain / double-acting window.
- Scheduler filters + binds under one lock, re-admits at snapshot time, covers taints/affinity/
  topology/resources (no double-bind, no binding to an unfit node). HPA clamps to min/max with
  stabilization. Job backoff/deadline/index caps faithful. Namespace lifecycle faithful (a stuck
  content finalizer blocking namespace deletion matches k8s).

**Runtime enforcement**
- SecurityContext → CRI: privileged, runAsUser/Group, capabilities add/drop, readOnlyRootFilesystem,
  no-new-privs (correctly distinguishing explicit `false` from absent), seccomp/apparmor/selinux,
  namespace options all reach the container/sandbox config (`pod-volumes.lisp:733-773`,
  `runtime.lisp:418-446`, `cri.lisp:230-248`).
- **runAsNonRoot re-checked at runtime** against the image's resolved UID; explicit `runAsUser:0`
  rejected, unknown image user fails closed (`pod-volumes.lisp:711-731`, `cri.lisp:700-708`).
- Resource limits → cgroups: CFS cpu-period/quota, cpu-shares, memory-limit, hugepage limits (unrequested
  sizes zeroed), cpuset from CPU-manager; reused on in-place resize (`container-resources.lisp:269-294`).
- Host namespaces/hostPath/subPath applied correctly; **subPath escape (CVE-2021-25741) hardened**
  with `openat2(RESOLVE_BENEATH|RESOLVE_NO_MAGICLINKS)` + realpath check + per-component mkdirat under
  pinned fds (`pod-subpaths.lisp:45-110`).
- CrashLoopBackoff 10→…→300s; startup probe suppresses liveness/readiness; exec probes run in-container;
  httpGet follows redirects only to the same host (blocks redirect-pivot SSRF). Image pull policy
  Always/IfNotPresent/Never honored with a shared-pull freshness window.
