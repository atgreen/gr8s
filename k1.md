# gr8s security / reliability / availability spot-check vs. upstream Kubernetes

**Date:** 2026-11-12
**Branch:** `http-client-aggregator`
**Reference:** upstream Kubernetes at `~/git/kubernetes`
**Method:** Targeted read-through of the auth, admission, TLS/PKI, secrets, NetworkPolicy,
and Raft/store code paths, comparing observed behaviour and implementation against
the equivalent upstream semantics. gr8s passes the 1.37 certification test; this note
deliberately looks past conformance at the security/reliability/availability posture the
cert test does **not** exercise.

## Overall assessment

This is a mature, security-conscious implementation. The hard, easy-to-get-wrong things are
done right: request authn/authz is faithful to k8s (including the v1.35 "exec is a `create`"
rule), mTLS does real chain verification everywhere (no parse-and-trust), admission webhooks
default **fail-closed**, Pod Security Admission covers init/ephemeral containers, the Raft
engine honours the etcd/Raft safety invariants k8s depends on, secrets support opt-in
AES-256-GCM at rest (exceeding the k8s default), and API Priority & Fairness is a real
seat/queue/429 implementation.

The findings below are therefore mostly **defense-in-depth gaps and deliberate deviations**,
plus **one confirmed HA-recovery regression** (F1, already tracked as `podster-k67`). None is a
remote unauthenticated compromise of a default single-node cluster.

## F1 — Snapshot-envelope tag mismatch breaks HA WAL recovery (High, availability)

**Root cause of open bug `podster-k67`.**

`src/resources/store-member-bootstrap.lisp:57` hand-builds the baseline snapshot envelope with
the tag `:gr8s-raft-snapshot`:

```lisp
(list :gr8s-raft-snapshot 1 :application reference :application-present t ...)
```

The vendored Raft library recognises **only** `:cl-raft-snapshot`
(`ocicl/cl-raft-20261111-648ea78/src/core.lisp:274`, `raft-snapshot-envelope-p`), and this is
the sole hand-rolled envelope in the tree:

- `:gr8s-raft-snapshot` → **1** occurrence in `src/` (this line)
- `:cl-raft-snapshot` → **0** occurrences in `src/` (every other envelope comes from the
  library's `raft-capture-snapshot`)

Every consumer tests via `raft-snapshot-envelope-p`, so the bootstrap baseline is rejected. A
fresh `--raft-init` founder (or a joiner learner) writes the stale-tagged baseline into its WAL,
then `validate-store-member-recovered-baseline`
(`src/resources/store-member-restore.lisp:184-188`) signals *"Application WAL recovery requires a
retained artifact baseline"* — exactly the symptom in `podster-k67`, reproduced by
`recovered-serve-reclaims-only-private-recognized-snapshot-scratch-before-listening`
(`tests/serve-state-ownership-test.lisp:248`). Even if the validator were bypassed,
`raft-restore-snapshot-contents` (core.lisp:290-305) would hand the whole envelope to
`restore-fn` instead of the artifact reference and would not adopt the founder's own membership
config — a genuine recovery-correctness break, not merely a failing test.

**k8s:** N/A (gr8s-specific HA layer), but the effect is an inability to bootstrap/recover the
multi-node control plane — an availability regression.

**Fix:** emit `:cl-raft-snapshot 1 ...` at `store-member-bootstrap.lisp:57` to match the migrated
library. One-line change; this is a library-rename that was not propagated into gr8s's one
hand-built envelope.

## F2 — No RBAC privilege-escalation prevention (High, security)

`validate-rbac-rules` and `validate-rbac-binding`
(`src/resources/bootstrap-resources.lisp:19,52`) validate only the **shape** of Role rules and
binding references. There is no equivalent of upstream's two escalation controls:

- **`escalate` on Role/ClusterRole writes:** k8s requires that a subject creating/updating a Role
  already holds every permission it grants, unless it has the `escalate` verb on
  `roles`/`clusterroles`.
- **`bind` on RoleBinding/ClusterRoleBinding writes:** k8s requires that a subject creating a
  binding already holds the referenced role's permissions, unless it has the `bind` verb on that
  role.

Neither check exists anywhere in `src/` (confirmed by grep — the only `escalat` hits are PSA's
`allowPrivilegeEscalation`).

**Impact:** whenever RBAC management is delegated to a non-`system:masters` subject — e.g. a
namespace admin granted `create`/`update` on `rolebindings` — that subject can bind an existing
powerful role (`edit`, `admin`, `cluster-admin`) to itself, or author a Role granting anything
and bind it, and escalate to full privileges. In upstream k8s this is exactly what the
`escalate`/`bind` checks prevent. Not exploitable in a default cluster (only `system:masters` can
write RBAC there), but it silently turns "let this team manage RBAC in their namespace" into "let
this team become cluster-admin."

**Fix:** implement rule-covering checks on Role/ClusterRole create/update and RoleBinding/
ClusterRoleBinding create, gated by `escalate`/`bind` verbs, mirroring
`plugin/pkg/auth/authorizer/rbac` + the RBAC REST escalation checks.

## F3 — No request body size limit → authenticated memory-exhaustion DoS (Medium–High, availability)

`read-complete-body` / `read-request-body` (`src/apiserver/http.lisp:1306-1340`) read the entire
request body into memory with **no maximum size**:

- With a `Content-Length` header, it allocates a buffer of exactly that many octets up front —
  `(make-array (or content-length 65536) ...)` — so a single request with
  `Content-Length: 2000000000` triggers a ~2 GB allocation **before the bytes even arrive**.
- For a chunked body it grows the buffer unboundedly (doubling) until EOF.

`read-request-body` runs at the very top of `answer-http-request` (http.lisp:1377), **before** the
APF seat is acquired, so API Priority & Fairness does not bound it.

**k8s:** caps request bodies via `limitedReadBody` (3 MiB default for most resources; larger for a
few). gr8s has no equivalent cap.

**Impact:** any authenticated client (any ServiceAccount token) can OOM the control plane with one
cheap request. Authenticated-only (the TLS acceptor authenticates before dispatch), so not an
unauthenticated DoS, but still a trivial availability attack.

**Fix:** reject with 413 when `Content-Length` exceeds a per-resource cap, and bound the chunked
read to the same cap.

## F4 — Secret volumes on persistent disk, not tmpfs (Medium, security)

`materialize-pod-volume` (`src/kubelet/pod-volumes.lisp:361-406`) backs `secret`, `projected`, and
`configMap` volumes by writing files to the on-disk pod volume directory
(`write-projected-volume-file`, mode `0600` files under a `0700` parent). Only
`emptyDir{medium:Memory}` and hugepages get a tmpfs mount (`pod-volumes.lisp:394-397` — verified).

**k8s:** backs Secret / projected / serviceAccountToken volumes with **tmpfs (medium Memory)** so
secret bytes never touch persistent storage and are wiped on reboot.

**Impact:** mounted secret/token material can survive on persistent media after a
crash-before-cleanup, be captured by disk-level node snapshots/backups, or be recovered from
stolen/decommissioned disks. Mitigated by `0600`/`0700` perms and `cleanup-pod-volumes` on
termination, which is why this is Medium rather than High.

**Fix:** mount secret/projected/SA-token volumes on tmpfs as upstream does.

## F5 — Egress policy bypass to API server, node IP, and node-local DNS (Medium, security; likely intentional)

In `src/network/egress-guard-program.lisp`, the DNS-gateway redirect (dst `169.254.1.1:53`) and
the `host_redirect_v4` redirect run at `:215-247` — **before** the NetworkPolicy gate at
`:251-281` — and `return (redirect ...)` first. `host_redirect_v4` contains the API server
ClusterIP `10.96.0.1` and the node's own IP (`src/network/host-redirect.lisp:25-34`).

**k8s:** a default-deny egress policy blocks the API server, node-local services, and DNS unless
explicitly allowed (famously breaks CoreDNS until a policy allows it).

**Impact:** a compromised Pod with default-deny egress still reaches the API server (attack
surface), node-hosted services, and DNS (exfiltration channel). This partly mirrors NodeLocalDNS
designs but is a weaker egress guarantee than k8s and should be an explicit, documented deviation.

## F6 — Ingress policy bypass for host-port/node-port traffic (Medium, security; plausible)

Host-port/node-port forwarding is a userspace relay (`src/network/pod-host-ports.lisp:8-149`).
Unless the port is `externalTrafficPolicy: Local` (which binds `IP_TRANSPARENT` to the client
address), the upstream connection to the Pod uses the node's kernel-selected source — on a
routed-CNI veth, the gateway `169.254.1.1`. The ingress guard **unconditionally allows** the
gateway source (`egress-guard-program.lisp:427`, and `:455-457` for `fe80::1`), skipping the
policy block entirely.

**k8s:** SNAT'd nodePort traffic appears as the node IP and is dropped by default-deny-ingress
unless the node IP is allowed.

**Impact:** external nodePort/hostPort traffic can reach a default-deny-ingress Pod.
**To confirm:** verify at runtime that the relay's connection to a routed Pod actually sources
from `169.254.1.1` (if it sources from the node's regular pod-facing IP, policy applies and this
is not a bypass).

## F7 — Fail-open on policy write failure / trie-cap exhaustion (Low–Medium, availability/security)

`write-pod-network-policy` (`src/network/network-policy.lisp:552-571`) writes the four CIDR/port
tries first and `netpol_mode` **last** (verified). `converge-pod-network-policies`
(`network-policy.lisp:590-608`) wraps each endpoint in a `handler-case` that only logs. For a
**newly created** Pod whose write throws mid-way — e.g. the egress LPM map hits its 16384 cap
(`egress-guard-program.lisp:126`) — `netpol_mode` stays zero-initialized ⇒ **allow-all**. The
projection expands each selector peer to one `/32` ipBlock per Pod, so a policy selecting
thousands of Pods can approach the cap.

**Impact:** a programming/capacity failure fails **open** (traffic allowed) rather than closed,
with no cap-exhaustion backstop or alarm.

**Fix:** on write failure, write `netpol_mode=1` with empty tries (fail closed) and alarm on
trie-cap exhaustion.

## F8 — No API audit logging (Medium, security/forensics)

No audit-log / audit-policy / audit-event / audit-sink support exists anywhere in `src/`
(confirmed by grep). k8s ships structured API audit logging (who did what, when, from where).

**Impact:** no way to reconstruct who created/modified/deleted resources, detect intrusion, or
meet compliance requirements. The cert test does not exercise audit, so this is invisible to
conformance.

## F9 — Single-node materialization writers skip the directory fsync (Low–Medium, reliability)

The consensus/durability path is correct: WAL appends fsync the file **and** the containing
directory before ack (`ocicl/cl-raft-.../src/log.lisp:91-98,295-297,453-463`), hard-state is
persisted before any reply, and followers fsync before replying with their match-index. The gap
is in the **materialization** writers that are the source of truth only in **single-node**
(non-HA) mode: `persist-pod`/`persist-node` (`src/store/persistence.lisp:247,268`),
`write-text-atomically` (`src/store/journal.lisp:87`), and `publications.lisp:39-40` fsync the
temp file but omit the **post-rename directory fsync**. A power cut after
`rename-file-overwriting-target` can lose the rename on some filesystems.

**Impact:** single-node only; in HA these files are rebuilt by re-applying committed WAL entries,
so it is not a consensus data-loss vector. The `pod-revision` ceiling is additionally protected by
over-reservation + `max(ceiling, object-revisions)` on reload.

**Fix:** fsync the containing directory after the rename in these writers, matching the WAL path.

## F10 — Latent unauthenticated API handler (Low)

`start-server` (`src/apiserver/server.lisp:191`) wires the full API handler (`handle-http-request`)
onto a loopback `gr8s-acceptor` whose dispatch (server.lisp:180) performs **no** authn/authz — the
auth gate lives only in the `gr8s-in-cluster-acceptor` subclass wrapper
(`src/apiserver/in-cluster-api.lisp:212`). This is the trust model of k8s's removed insecure port.
CSR-signer authorization is specifically gated on the request arriving via the in-cluster acceptor
type (`csr-http.lisp:92`), so the base handler would also bypass CSR RBAC.

`start-server` has **no callers** in `src/`, `tests/`, or `scripts/` (confirmed), so it is latent,
not a live exposure — but the auth-free code path exists and could be wired to a listener.

**Fix:** delete `start-server`, or route it through the authenticating acceptor, so no code path
reaches `handle-http-request` without the auth gate.

## F11 — No certificate revocation with long leaves (Low)

`check-revocation` defaults NIL and there is no CRL/OCSP infrastructure; node/member/signed-CSR
leaves live up to ~365 days (`csr-signer.lisp:78-80`). A compromised key is usable until expiry.
This matches the upstream k8s model (short-lived certs + Node deletion), but 1-year leaves are on
the long side for a revocation-free system — consider shorter default lifetimes.

## F12 — IP-fragment port evasion (Low, plausible)

Both guards read L4 ports at a fixed offset gated only on `ihl=5` and byte-bounds
(`egress-guard-program.lisp:265-268,402-405`), without checking the IPv4 fragment-offset / MF
field. A non-first fragment's payload is misread as ports, and the port match is stateless, so a
crafted fragmented flow to/from an allowed CIDR peer could slip past port restrictions (CIDR match
still applies). Mirrors a known limitation of simple eBPF firewalls (Cilium uses frag-tracking).

## F13 — Datapath test-coverage gap (Info)

`compile-network-policy*` / `resolve-pod-policy` / `compile-pod-policy`
(`src/network/network-policy-program.lisp`) — the stateless classifier — are referenced **only**
in `tests/` and `scripts/probe-network-policy.lisp`, never in `src/`. The shipping enforcement is
the map-driven `gr8s-egress-guard`/`gr8s-ingress-guard`. So the privileged end-to-end probe
exercises a non-production path; the real datapath (stateful `netpol_flows`, `except` handling,
port ranges, IPv6) is covered only by unit tests of the map-content builders. Recommend an
end-to-end probe against the attached guards covering `except`, port-range, stateful-reply, and
IPv6.

## F14 — Voter enrollment key blast radius (Info)

Voter enrollment ships the CA private key, node-CA key, and SA signing key as plaintext PEM in the
(TLS-protected, one-time-token + node-name + role gated) gRPC response
(`src/security/raft-tls.lisp:126-141`). Correct for the HA "a voter can admit replacements" model
and properly gated, but a large blast radius for a single leaked voter token — worth documenting.

## Verified correct (faithful to k8s)

Spot-checks that came back clean are worth recording so effort isn't re-spent:

- **Request authn/authz gate** on the TLS listener: client-cert + bearer-token → RBAC, including
  the v1.35 exec/attach/portforward-is-`create` rule, trace/slynk-is-`create` remaps, non-resource
  URL handling, and field-selector name scoping (`in-cluster-api.lisp`, `service-account.lisp`).
- **RBAC rule evaluation** and the **node authorizer** (a kubelet may only `get` Secrets/
  ConfigMaps/PVCs referenced by Pods bound to its own node; token/access reviews allowed) —
  faithful to upstream's Node authorizer (`service-account.lisp:389-407`).
- **Admission webhooks**: config defaulting makes `failurePolicy` default to **Fail** (fail-closed)
  like k8s v1; validating webhooks run concurrently; mutating chain reinvokes with `IfNeeded`
  (`admission-resources.lisp:226`, `admission-webhooks.lisp`).
- **Pod Security Admission**: baseline + restricted, correctly covering `containers`,
  `initContainers`, **and** `ephemeralContainers`, with version-gated checks and namespace-label
  grandfathering (`pod-security-admission.lisp`).
- **mTLS**: every path does real `verify-certificate-chain` (dates, CA bit, pathlen,
  signature-anchored to the trust store, EKU). The `+verify-none+` at the pure-tls handshake layer
  is always immediately followed by an explicit application verifier inside a `handler-case` that
  closes the stream on failure. Client-cert→identity maps CN→user and O→groups only (never SANs);
  `system:masters` is blocked at the client signer. CA keys `0600`/`O_EXCL`; secret comparisons
  constant-time.
- **CSR flow**: approval RBAC-gated on `approve` verb on `signers/<name>` (incl. domain wildcard),
  direct status writes need `sign`; leaves get CA:FALSE + bounded EKU + ≤365d lifetime. gr8s ships
  no auto-approver, so the classic auto-approved node-cert spoofing path does not exist.
- **Secrets**: opt-in AES-256-GCM at rest (per-object nonce, AAD binding
  resource/namespace/name/keyId, proper key-rotation lifecycle) — exceeds the k8s default;
  consistent `0600`/`0700` perms; bound projected tokens validate `iss`/`exp`/`nbf`/`aud` +
  signature and re-check live UID binding; constant-time opaque-token compare; no secret material
  in logs.
- **Raft safety**: commit advances only on a quorum of a current-term entry (§5.4.2); vote
  persisted (fsync) before responding; Pre-Vote + CheckQuorum; single-server membership changes
  gated on a committed current-term entry and one-change-in-flight; log-matching/truncation never
  overwrites committed entries; torn-frame recovery is checksum-validated and refuses ambiguous
  repairs. Store/raft commit failures surface as 503/413 without crashing the apiserver
  (fail-closed).
- **API Priority & Fairness**: real seat accounting, queueing, and 429 + Retry-After; exempt and
  long-running requests take no seat (`flowcontrol.lisp`).
- **NetworkPolicy core semantics**: default-deny-on-select, additive union of policies, empty vs
  absent selectors, ipBlock+except via LPM, ingress/egress independence, named ports resolved in
  the correct direction, TCP/UDP/SCTP + endPort, and conntrack-style stateful replies — all
  correct and genuinely wired to the eBPF datapath. Pod-to-pod is WireGuard-encrypted with per-peer
  AllowedIPs, so a compromised node can spoof only its own CIDR.
